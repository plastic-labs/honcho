<Warning>
Ingest and auto workspaces are experimental and under active development, and available only on self-hosted Honcho for now. The API, SDK methods and CLI commands described here may change or stop working without notice, and aren't ready for production use. The CLI's ingest commands are off by default: set `HONCHO_EXPERIMENTAL=1` to run them. See [Auto Workspaces](/v3/contributing/experimental/auto-workspaces) for what works today and the server it needs.
</Warning>

Ingest turns records from another system (a chat message, a meeting note, an event) into Honcho messages. You send the record as the source has it: who wrote it, where it lives, and its ID in the source. Honcho picks the session and peers for you:

- A record's container (a channel, a thread) becomes its session.
- Each author and participant becomes a peer, matched across records by their ID in the source.
- Each record is deduplicated on its source identity, so sending the same records again is always safe.

Ingest writes only to an **auto workspace**. A workspace is auto only if it was created that way; an existing regular workspace can't be switched.

## Create an auto workspace

Pass `auto` when you create the client. The workspace is created as auto on the client's first call. On an existing workspace that isn't auto, that call fails with a conflict error.

<CodeGroup>
```python Python
from honcho import Honcho

honcho = Honcho(workspace_id="team-chat", auto=True)
```

```typescript TypeScript
import { Honcho } from '@honcho-ai/sdk';

const honcho = new Honcho({ workspaceId: 'team-chat', auto: true });
```
</CodeGroup>

A client without `auto` can still ingest into a workspace that is already auto. It won't create one: ingesting into a workspace that doesn't exist is a not-found error.

## Ingest records

Pass any number of records. The SDK sends them 100 per request and returns one result per record, in the order you passed them.

<CodeGroup>
```python Python
result = honcho.ingest(
    [
        {
            "source": "discord",
            "source_instance": "1016845",          # the server, team or account
            "source_id": "1567641475",             # the record's ID in the source
            "created_at": "2026-11-04T20:47:00Z",
            "container": {"id": "1145750626", "name": "dev"},
            "author": {"id": "8812", "name": "Jessica"},
            "content": "the deploy is done",
        }
    ]
)

for record in result.records:
    print(record.index, record.outcome, record.session_id, record.peer_id)
```

```typescript TypeScript
const result = await honcho.ingest([
  {
    source: 'discord',
    sourceInstance: '1016845', // the server, team or account
    sourceId: '1567641475', // the record's ID in the source
    createdAt: '2026-11-04T20:47:00Z',
    container: { id: '1145750626', name: 'dev' },
    author: { id: '8812', name: 'Jessica' },
    content: 'the deploy is done',
  },
]);

for (const record of result.records) {
  console.log(record.index, record.outcome, record.sessionId, record.peerId);
}
```
</CodeGroup>

Each result's `outcome` is `created`, `duplicate` (already stored) or `rejected`, with a `reason`. If a request fails partway through a large import, the batches before it are already stored; send all the records again and the stored ones come back as duplicates.

Mark accounts the source flags as bots or integrations with `bot: true` on the author or participant. Their messages are stored and read as context, but nothing is derived about them.

Bots also post a lot that nobody answers, and that text still costs tokens as context. The Python SDK's `filter_bot_records(records)` keeps a bot's record only when a person interacted with it: a reply chain with a person in it (`metadata.reply_to` names the `source_id` replied to), or a person @-mentioning the bot in the same conversation (the bot is in their `participants` and their text names it, `@name` or Discord's `<@id>`), which keeps the bot's post before the mention and its answer after. A conversation is the session the record goes to (its `session_id`, else its container, else the record on its own), narrowed by `metadata.thread` when it has one. It returns the records to send and how many it held back; `keep="all"` or `keep="none"` keep every bot record or none. `honcho ingest import` applies it by default (`--bots interacted`).

## Load first, derive later

With `derive="later"`, records are stored without being reasoned about. Nothing is derived until you release them, so you can check how the import was organized before paying for reasoning, and peer and session configuration changes made in between apply to what's derived.

<CodeGroup>
```python Python
honcho.ingest(records, derive="later")

# ... review peers and sessions, exclude what shouldn't be modeled ...

released = honcho.ingest_derive()
print(released.pending, released.remaining)
```

```typescript TypeScript
await honcho.ingest(records, { derive: 'later' });

// ... review peers and sessions, exclude what shouldn't be modeled ...

const released = await honcho.ingestDerive();
console.log(released.pending, released.remaining);
```
</CodeGroup>

`ingest_derive()` releases deferred records in batches until none remain, then returns how many it released. Track reasoning progress with [queue status](/v3/documentation/features/advanced/queue-status).

## Review an import before deriving it

Between loading and deriving, check what the records became: how many are waiting, which people and sessions they map to, and which of those are modeled. People and sessions are listed most records first.

<CodeGroup>
```python Python
from honcho.api_types import PeerConfig

status = honcho.ingest_status()
print(status.records.deferred, status.deferred_tokens, status.people, status.sessions)

for person in honcho.ingest_people():
    print(person.display_name, person.peer_id, person.messages, person.modeled)

# A bot the source didn't flag: derive nothing about it.
honcho.peer("usage-stats-9a1b2c3d4e").set_configuration(PeerConfig(observe_me=False))
```

```typescript TypeScript
const status = await honcho.ingestStatus();
console.log(status.records.deferred, status.deferredTokens, status.people, status.sessions);

for await (const person of await honcho.ingestPeople()) {
  console.log(person.displayName, person.peerId, person.messages, person.modeled);
}

// A bot the source didn't flag: derive nothing about it.
await (await honcho.peer('usage-stats-9a1b2c3d4e')).setConfiguration({ observeMe: false });
```
</CodeGroup>

Excluding a person (`observe_me` off) or a session (reasoning off) before `ingest_derive()` keeps it out of what is derived: configuration is read when records are released. After release, an exclusion only affects records released later; conclusions already derived stay.

## One person, several accounts

The same person can show up as two accounts: Alex on Discord and alexdev on GitHub. Linking them makes every account of the other people map to the first, so the next import puts their records on one person. A link never moves what was already imported, so during a dry run you reset, link, and import again; before anything is derived that costs nothing.

<CodeGroup>
```python Python
honcho.ingest_reset()  # deletes the imported sessions; people, their exclusions and links stay
# ... wait until ingest_status().sessions_being_deleted is 0 ...
honcho.ingest_link(["alex-018a0fc9e0", "alexdev-41c0b2d7e1"])
honcho.ingest(records, derive="later")  # Alex now has both accounts
```

```typescript TypeScript
await honcho.ingestReset();
// ... wait until (await honcho.ingestStatus()).sessionsBeingDeleted is 0 ...
await honcho.ingestLink(['alex-018a0fc9e0', 'alexdev-41c0b2d7e1']);
await honcho.ingest(records, { derive: 'later' });
```
</CodeGroup>

`ingest_unlink()` takes one account back out the same way. A link is refused while the people being merged have imported messages (reset first), or once anything has been derived about them. A reset deletes the imported sessions in the background, with their messages; people, their exclusions and links stay, and a session's own settings go with it.

### Suggested links

Honcho can suggest which accounts are one person, with the evidence: the same email, an account that gives its handle on another source as its own ("I'm alexdev on GitHub"), names only those two accounts share, or someone linking their own pull requests right after opening them. `ingest_refresh_suggestions()` queues a refresh that reads the imported records, so run it after importing and before a reset. `ingest_suggestions()` lists them, strongest first: `high` ones have evidence to accept at a glance, `low` ones need a closer look. Accepting one is a link, refused the same way while the people have imported messages; a dismissed one never comes back. Nothing is linked until you accept. A walkthrough with two sources is in [One Workspace from Several Sources](/v3/contributing/experimental/ingest-sources).

<CodeGroup>
```python Python
honcho.ingest_refresh_suggestions()
# ... wait until ingest_status().suggestions.refreshing is False ...
for s in honcho.ingest_suggestions(confidence="high"):
    print([a.display_name for a in s.accounts], [e.detail for e in s.evidence])
honcho.ingest_reset()
# ... wait for the reset ...
honcho.ingest_accept_suggestion(s.id)
honcho.ingest(records, derive="later")
```

```typescript TypeScript
await honcho.ingestRefreshSuggestions();
// ... wait until (await honcho.ingestStatus()).suggestions.refreshing is false ...
const page = await honcho.ingestSuggestions({ confidence: 'high' });
await honcho.ingestReset();
// ... wait for the reset ...
for (const s of page.items) await honcho.ingestAcceptSuggestion(s.id);
await honcho.ingest(records, { derive: 'later' });
```
</CodeGroup>

## From the CLI

The [Honcho CLI](/v3/documentation/reference/cli) runs the same flow on a connector's `records.jsonl`. These commands are experimental, so they run only with `HONCHO_EXPERIMENTAL=1` set:

```bash
export HONCHO_EXPERIMENTAL=1
honcho workspace create acme --auto
honcho ingest import records.jsonl -w acme
honcho ingest status -w acme
honcho ingest suggestions -w acme                # accounts that look like one person
honcho ingest suggestions accept 1 --reset -w acme   # links them: resets the import
honcho ingest link 1 2 --reset -w acme          # or link two people yourself
honcho ingest import records.jsonl -w acme       # their records now go to one person
honcho ingest status -w acme                     # numbers change after a reset
honcho peer exclude "Usage Stats" -w acme
honcho session exclude 12 -w acme                # after the last reset: a reset deletes sessions
honcho ingest derive -w acme --watch
```

`honcho ingest import FILE --check` validates a file without a workspace or credentials and sends nothing. Installed connectors run straight from the CLI: `honcho ingest from` lists them, and `honcho ingest from github --repo OWNER/NAME --token-file FILE -w acme` reads and imports in one step, holding back unanswered bot records the same way. To write your own exporter or connector, see [Writing an Exporter](/v3/contributing/experimental/ingest-exporters).
